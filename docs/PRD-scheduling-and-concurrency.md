## 1. 产品目标

**一句话**：把「什么时候把任务交给 worker」和「同一个 key 在同一个模型上能同时压多少任务」变成可控旋钮，让本服务从一个「收到就发」的透传队列，升级为一个能主动整形流量的调度层。

现状的痛点是三个真实场景，今天都无解：

1. **突发提交打爆上游渠道**。客户端一次性提交几百条出图任务，本服务照单全收、立刻全部入队，worker 以 64 并发直冲上游。上游单渠道的并发配额被瞬间打满，触发的是上游的 429/5xx，而本服务把它如实落成 `FAILURE` 返给客户端——用户看到的是「服务不稳定」，实际是我们没有节流。
2. **贵模型与廉价模型共享同一个水位**。当前唯一的并发闸门是「单 token 在途 ≤ 10」，不区分模型。一个 key 用 10 个槽全压在某个渠道容量只有 2 的高价视频模型上，既打爆了那个渠道，也让该 key 的其他廉价出图请求全部 429。粗粒度闸门同时造成了「拦不住该拦的」和「误伤不该拦的」。
3. **没有低峰期概念**。长耗时生成任务（60~180s 一条）天然适合错峰跑批，但客户端目前唯一的选择是「现在就提交」。想在凌晨跑 500 张图，只能自己写定时器和重试逻辑——而重试逻辑写错就是重复调上游、重复扣费（钱在上游扣，我们连止损都做不到）。

三项需求正好覆盖这三个痛点，且互相咬合：**并发维度**定义了水位线在哪里，**批量聚合**决定水位以什么节奏被填满，**延迟/定时**让客户端可以主动把负载挪到水位空闲的时段。

**不解决的问题**（避免期待错位）：不提升上游吞吐、不做任务优先级抢占、不做跨 key 的公平调度、不合并上游调用。

## 2. 用户故事

### 角色 A：接入方开发者（调用 `/async` 的应用）

**A1 — 错峰跑批出图**
作为电商素材团队的开发者，我在白天配置好当晚要生成的 800 张商品图，希望它们在凌晨 2 点自动开始跑，早上上班时结果已就绪，而不是我自己起一个 crontab 在半夜调接口。
*验收线索*：提交时带上目标执行时刻，接口立刻返回 202 + task_id；在到点前查询该 task_id 返回 202 且能看出「还没开始、计划何时开始」；到点后任务自动进入执行；从提交到执行的整个等待期，我随时可以取消其中任意一条。

**A2 — 一次性提交一批，希望被平滑执行**
作为批处理作业的开发者，我一次提交 500 条 TTS 任务。我不希望它们被一股脑塞给上游导致大面积失败，也不希望我自己在客户端写限速逻辑。
*验收线索*：这 500 条全部返回 202；它们不会同时进入执行，而是按服务端配置的批次与并发节奏分批放行；任何一条的查询、取消、回调、幂等行为与普通任务完全一致；最终全部执行完，没有任何一条因为「排队太久」被静默丢弃或误判死。

**A3 — 我知道我这批有多少条**
作为一个已知作业规模的开发者，我希望声明「这批共 200 条，凑齐就一起放行」，让整批任务在时间上尽量对齐，方便我做整体的结果收集。
*验收线索*：显式声明批次标识与期望条数；凑够即放行；若我只发了 150 条就崩了，服务端在等待上限到达后必须放行这 150 条，绝不能让它们永远挂着。

**A4 — 我不想改代码就能享受保护**
作为一个已经上线的接入方，我不带任何新参数继续提交时，行为必须和今天一模一样。
*验收线索*：不带新增请求头的提交，其响应码、响应体、Location、幂等语义、429 语义全部与当前版本逐字节一致。

### 角色 B：平台运营

**B1 — 按模型设水位，保护上游渠道**
作为运营，我知道 `sora-video` 这类模型上游只有 2 路并发，而 `dall-e-3` 有 30 路。我要能给不同模型设不同的单 key 并发上限，而不是所有模型共用一个数字。
*验收线索*：可以为指定模型设定单 key 在途上限，配置在管理看板上可见、可改、改完即时生效不重启；未单独配置的模型回落到全局默认值。

**B2 — 看得见谁在占水位**
作为运营，当接入方投诉「我一直被 429」，我要能在看板上直接看到这个 key 在哪个模型上占了多少槽、上限是多少，而不是去 SSH 上翻 Redis。
*验收线索*：管理看板能按模型与 key 维度展示当前在途占用与上限；能看到计划中（尚未到执行时刻）和批次等待中的任务数量。

**B3 — 单 key 不能横向扩模型绕过限制**
作为运营，我不接受「每个模型限 10 个，于是一个 key 同时用 8 个模型压 80 个在途」这种绕过方式。
*验收线索*：细粒度上限之外仍存在一个跨模型的总量上限；两层任一超限即拒绝。

### 角色 C：服务 SRE

**C1 — 计划任务不能吃掉在途资源**
作为 SRE，我绝不接受一个延迟 4 小时的任务从提交那一刻就占住一个并发槽——那等于用户提交 10 条延迟任务就把自己的配额锁死 4 小时，正常请求全部 429。
*验收线索*：处于等待期（延迟未到点、批次未放行）的任务不计入任何并发槽计数；只有在真正放行入队的那一刻才占槽；槽位校准任务的事实源口径必须与之一致，不能把等待期任务算进活跃数。

**C2 — 兜底机制不能误伤新语义**
作为 SRE，现有的两个兜底扫描是按「非终态 + 长时间没动静 = 出事了」的假设写的。计划任务天然就是「长时间没动静」，我需要确认它们不会被提前执行或被判死。
*验收线索*：一个延迟 3 小时的任务，在等待期内不被 `sweep_stale` 重投执行，也不被 `sweep_overdue` 判死；到点后正常执行；若到点后仍卡住，兜底机制照常生效。

**C3 — 取消不能造成槽位账目错乱**
作为 SRE，我要求取消一个从未占槽的等待期任务时，不能去释放一个它没占过的槽。
*验收线索*：取消等待期任务后，该 token 与该 (模型,token) 的槽计数保持不变；同 token 的其他在途任务不受影响；一轮槽位校准后计数与 DB 事实一致。

## 3. 需求池

字段约定：所有新增持久化字段一律落在 `tasks.data` JSON 列或 Redis，**不建任何 MySQL 表**（SPEC §3 铁律）。所有新增请求头**一律可选**，不带即现状行为。

### P0 — 本轮必须交付

| ID | 需求 | 产品定义 | 验收线 |
|---|---|---|---|
| R-01 | 相对延迟提交 | 请求头 `X-Delay-Seconds: <int>`，表示自提交起延迟 N 秒执行。0 或不带 = 立即执行 | 202 立即返回；到点误差 ≤ 30s；`data.scheduled_at` 落库 |
| R-02 | 绝对定时提交 | 请求头 `X-Execute-After: <unix秒 或 RFC3339>`，指定不早于该时刻执行。与 R-01 同时出现 → 400 | 同上；过去时间视为立即执行，不报错 |
| R-03 | 延迟上限与校验 | 延迟量超过 `max_delay_seconds`（默认 6h）→ 400，错误码 `delay_too_long`。上限可热改，配置硬上限 12h | 超限即拒；边界值可提交 |
| R-04 | 等待期不占并发槽 | 计划任务在提交时**不占**任何并发槽；只在放行入队的瞬间占槽 | 提交 20 条延迟任务后，该 token 槽计数仍为 0；立即提交仍受槽约束 |

| R-07 | 等待期可取消且账目正确 | 等待期任务的取消行为与现状一致（`QUEUED → CANCELED`），但**不得释放未占用的槽** | 取消后 token 槽计数不变；同 token 其他在途任务不受影响 |

## 4. API 契约变更草案

### 4.1 新增请求头（全部可选，作用于 `POST/PUT /async/{path}`）

| 头 | 取值 | 语义 | 非法时 |
|---|---|---|---|
| `X-Delay-Seconds` | 非负整数 | 自提交起延迟 N 秒执行 | 非整数/负数 → 400 `invalid_delay`；超上限 → 400 `delay_too_long` |
| `X-Execute-After` | unix 秒整数 或 RFC3339 | 不早于该时刻执行；过去时刻视为立即 | 无法解析 → 400 `invalid_execute_after`；超上限 → 400 `delay_too_long` |
| `X-Batch-Key` | 字符串 ≤64 字符 | 批次归组键 | 超长 → 截断至 64（不报错，与 `Idempotency-Key` 现有处理一致） |
| `X-Batch-Size` | 正整数 | 期望批量 N | 非正整数 → 400 `invalid_batch_size` |
| `X-Batch-Wait` | 正整数秒 | 最长等待 T | 超上限 → 400 `batch_wait_too_long` |

**互斥规则**：`X-Delay-Seconds` 与 `X-Execute-After` 同时出现 → 400 `conflicting_schedule_headers`。调度（延迟/定时）与聚合（批次）**可以叠加**，语义为：先等到计划时刻，再参与批次聚合。

### 4.2 变更的响应体（增量字段，不删不改现有字段）

`202` 响应体（提交与查询共用视图）新增：

```json
{
  "task_id": "dall_e_3_ab12...",
  "status": "QUEUED",
  "created_at": 1730000000,
  "scheduled_at": 1730003600,
  "batch_key": "nightly-batch-01",
  "batch_state": "waiting"
}
```

- `scheduled_at`：0 表示无延迟。老客户端忽略未知字段，不受影响。
- `batch_key` / `batch_state`：无批次时为空串。

### 4.3 新增错误码

`invalid_delay`、`delay_too_long`、`invalid_execute_after`、`conflicting_schedule_headers`、`invalid_batch_size`、`batch_wait_too_long`。全部走现有统一错误体 `{"error":{"message","type","param","code"}}`，HTTP 状态码均为 400。

### 4.4 新增管理端点

| Method | Path | 功能 |
|---|---|---|
| GET | `/admin/api/schedule` | 计划中任务概览（按时间桶）+ 等待中批次列表 |
| GET | `/admin/api/slots` | 按 (模型,token) 的在途占用/上限 Top N |
| POST | `/admin/api/batches/{batch_key}/release` | 手工立即放行（P2） |

模型级并发上限的读写复用现有 `/admin/api/config`，但**现有 dynconf 白名单只支持标量类型**（`int/float/bool/str`），存不下「模型 → 上限」的映射。这是一个需要架构裁决的机制缺口，见 §6 Q4。

### 4.5 不新增状态

**明确决策：不引入 `SCHEDULED` / `BATCHING` 等新状态，等待期任务保持 `QUEUED`。**

理由：
1. `QUEUED` 取自 new-api 原生 `TaskStatus` 枚举（ADR-006 共存约束），自造状态值会让共享 `tasks` 表上的上游看板与 SQL 巡检读到未知值；
2. 新状态会牵动 `ACTIVE`/`PENDING` 元组、所有 CAS 迁移合法起点、`admin/api/tasks` 的 status 正则、取消判定分支——改动面远大于收益；
3. 客户端要区分「排队中」与「计划中」，靠 `scheduled_at` 字段即可，语义更精确（还能知道**何时**开始），也不破坏任何现有契约。

代价是 admin 列表按 status 筛选时看不出差异，由 R-21 的独立调度视图补齐。

### 4.6 对现有 AC-01 ~ AC-36 的破坏性评估

**结论：不带任何新增请求头的请求，行为逐字节不变，AC-01~AC-36 全部继续成立。**

需要**修订**的既有条款有两条，均为兜底逻辑与新语义的冲突，必须在实现前正式变更：

| 条款 | 冲突 | 要求的修订 |
|---|---|---|
| **AC-33**（卡死兜底） | 现文「长时间无进展且未被标记待对账的非终态任务必须标记收敛」。计划任务天然长时间无进展，会被 `sweep_stale` 提前重投执行，直接摧毁延迟语义 | 加豁免条件：**尚未到达 `scheduled_at` 的任务不属于卡死**，兜底扫描必须跳过 |
| **AC-18/AC-24**（终态释放槽） | 现文要求终态一律释放并发槽。等待期任务从未占槽，取消时释放会还掉同 token 其他在途任务的槽，造成并发超卖（`LUA_SLOT_RELEASE` 的下溢保护挡不住这种「有余额时的误扣」） | 加限定：**仅当任务实际占用过槽（`data.inflight_slot=true`）时才释放**；释放范围同时覆盖 token 层与 (模型,token) 层 |

需要**语义重定义**（不算破坏，但必须同步文档与默认值）的有一条：

| 条款 | 变化 |
|---|---|
| **AC-08**（超限 429） | 429 触发条件由「token 在途达上限」扩展为「token 总在途达上限 **或** (模型,token) 在途达上限」。行为（429 + `Retry-After`）不变。配套 `MAX_SLOTS` 默认值由 10 上调至 30，否则内层维度不可能生效 |

其余条款（AC-01~AC-07、AC-09~AC-17、AC-19~AC-23、AC-25~AC-32、AC-34~AC-36）无影响。特别确认：
- **AC-05/AC-06（幂等）**：`task_id` 计算式不变（`slug + sha256(token_hash|key)`），调度头不参与计算。同 key 重放返回原 task_id，且**不重复加入批次、不重排计划时刻**——重放就是重放，不是重新调度。
- **AC-19（查询 202）**：等待期任务查询仍返 202，只是响应体多了增量字段。
- **AC-24（排队中可取消）**：等待期任务仍是 `QUEUED`，天然可取消，这是延迟功能最重要的安全阀。

## 6. 待确认问题

### Q1（必答）— `token_hash` 全局槽在新维度上线后：保留还是替换？

**产品建议：保留，作为外层兜底，形成「token 总量 + (模型,token) 细粒度」双层闸门。同时必须把 `MAX_SLOTS` 默认值从 10 上调至 30 并重新定义其语义。**

理由：

1. **只有细粒度层拦不住横向扩散**。这是决定性论据。假设只保留 (模型,token) 层、每模型上限 10，一个 key 同时使用 8 个模型就能合法地压 80 个在途任务。本服务单 worker 并发是 64，上游总容量也是有限的——单 key 就能把整个服务的执行能力吃干。细粒度维度解决的是「别在某个渠道上扎堆」，它在设计上就不负责「总量封顶」，两者不可互相替代。
2. **删除的改造成本高于保留**。现有 `recalibrate_slots` 的事实源 `active_counts_by_token()` 就是按 `token_hash` 分组，admin 详情页的 `slots_in_use` 也读它。保留 = 这两处零改动，只需**增量**新增一个维度；替换 = 要重写校准、改 admin 视图，还要处理灰度期新旧键并存的迁移。收益为零的重构。
3. **成本极低**。多一次 Redis 计数操作，在提交链路 P99 < 80ms 的预算里可忽略。
4. **保留即降级路径**。若细粒度层因配置错误全线放开，外层仍能兜住底；反之若只有细粒度层，一次误配就是无限敞口。

**但保留有一个必须同步做的配套动作，否则上线即回归**：`MAX_SLOTS` 当前默认 10，语义是「单 token 在途上限」。如果外层维持 10 不变，而内层每模型也给 10，那么内层永远不可能先触发——外层 10 个槽就是天花板，细粒度维度完全是摆设，我们做了一堆工作而用户感知不到任何变化。因此：

- `MAX_SLOTS` 语义重定义为「单 token **跨全部模型**总在途上限」；
- 默认值上调至 30（= 允许一个 key 大致同时在 3 个模型上跑满默认细粒度额度）；
- 该默认值调整需要运营与 SRE 确认是否与当前上游总容量匹配。

**需要架构侧（高见远）评估的风险**：双层占槽的原子性与回滚——外层占成功、内层失败时必须归还外层，这是一个跨两个 Redis 键的复合操作。若无法做成单次原子操作，需要明确失败窗口的影响面与收敛手段（校准任务能否覆盖）。这条直接影响 AC-50 的可实现性。

### Q2 — 超限时维持 429 硬拒，还是转为服务端排队等待？

**产品建议：维持 429 硬拒（AC-08 语义不变）。**

理由：

- 转排队是**重大语义变化**。今天客户端拿到 429 就知道「我该退避重试」；改成排队后，客户端拿到的是 202 + task_id，但这个任务可能几小时后才跑。客户端无从判断该等还是该放弃，超时策略、重试策略全部要重写——而这些接入方今天已经按 429 上线了。
- 排队需要一整套本 PRD 未覆盖的机制：排队存储、队首公平性、饥饿防护、排队上限、排队超时。这些的复杂度不亚于三项需求本身。
- **更重要的是：本次三项需求已经提供了排队的等价能力，而且语义更干净**。客户端想要「不被拒、我愿意等」，可以显式用 `X-Delay-Seconds` 或批量聚合——等待发生在**客户端明确选择**的时间维度上，而不是服务端隐式挂起。这比服务端偷偷排队更可控，也更好排障。
- 若确有强诉求，走 P2 的 R-23（`X-On-Slot-Exhausted: defer`）作为**显式选择加入**的逃生舱，默认仍是 `reject`。这样语义变化只发生在主动声明的客户端上。

### Q3 — 延迟上限取多少？生命期口径怎么改？

**产品建议：`max_delay_seconds` 默认 6h，配置硬上限 12h；`sweep_overdue` 的计时起点改为 `max(created_at, scheduled_at)`（R-06 / AC-45）。**

理由与约束推导：上游 new-api 有 24h 任务清理线，本服务必须先于它收敛自己的行（`sweep_overdue` 的存在理由）。因此必须满足：

```
最大延迟 D + 任务最大生命期 L < 24h（上游清理线），且要留足余量
```

`L` 默认 6h，若 `D` 也取 6h，则最坏 12h 收敛，余量 12h，安全。若 `D` 取到硬上限 12h，则最坏 18h，余量 6h，仍可接受但不建议作为默认值。

**若不修 R-06 的计时口径，延迟功能实际上限只有约 6h 减去执行时间，且任何延迟超过 6h 的任务会被静默判死**——这是必须修的，不是可选项。请架构侧确认这个口径修改是否会影响 `overdue_active()` 的 SQL 索引命中（`created_at` 上有索引，改成 JSON 字段的 `max()` 比较可能走全表扫）。这是一个真实的性能风险点。

### Q4 — 模型级并发上限的配置存储机制

现有 `dynconf.MUTABLE` 白名单只支持 `int/float/bool/str` 四种标量，`RuntimeConfig` 是一个扁平 dataclass 快照。「模型 → 上限」是一个映射，塞不进去。

**产品倾向：扩展 dynconf 支持一种 `json` 类型的 Spec，带条目数上限与值域校验，仍走白名单机制。**

理由：另开一套配置存储会造成运营认知分裂（有些旋钮在配置页、有些在别处），也会绕开 ADR-005 建立的「白名单 + 整批校验 + 整批回退」安全模型。但扩展类型系统涉及 ADR-005 的边界，需要架构侧裁决：是扩展 dynconf，还是承认这是一份「运营数据」而非「配置」，单独设计存储与管理端点。

### Q5 — 批次默认归组键选 `token_hash + model` 是否合适？

**产品倾向：是。** 默认归组键与并发维度（model × token）对齐，语义自洽——同一批放行的任务竞争的是同一个并发窗口，凑批填满窗口才有意义。若默认只按 token 归组，一个批次里混了 8 个模型的任务，放行后它们分散到 8 个不同的并发窗口，凑批完全没起到削峰作用。

需要确认的是：是否存在「跨模型作业级批次」的真实场景（例如一个工作流先出图再配音）。若有，`X-Batch-Key` 已能覆盖，但需要确认接入方是否理解「跨模型批次不保证同时执行」。

### Q6 — 提交限流 60/60s 与「突发 500 条」场景直接冲突

这是一个会让功能上线即无法使用的隐患，必须先解决。当前 `rate_limit` 默认 60 次/60 秒按 token_hash 计。用户故事 A2 的「一次提交 500 条」在**第 61 条就会被 429 挡在提交阶段**，根本走不到批量聚合逻辑。

**产品倾向：不在本 PRD 内改限流默认值**（那是另一个风险决策），但必须做两件事：
1. 在接入文档中明确：使用批量聚合前需与运营确认该 key 的提交速率配额；
2. 请运营给出批量场景的推荐配额档位（例如 600/60s），并确认提交链路 P99 < 80ms 的性能目标在该速率下仍成立。

请 SRE 确认高提交速率下 MySQL 连接池预算（SPEC §10：`进程数 × (pool_size + max_overflow) ≤ max_connections × 0.8`）是否还够。

### Q7 — 批次放行是否需要保序？

**产品倾向：本轮不承诺任何顺序保证**（P2 / R-25）。理由：放行只是入队，worker 是 64 并发，即使入队有序，执行完成顺序也必然乱序。承诺一个客户端感知不到的顺序没有意义，反而给实现加约束。若接入方有强顺序需求，应拆成串行提交。

### Q8 — SPEC §6 与 AC-19/AC-24 的 `SUBMITTED` 状态名勘误

代码中的实际常量是 `QUEUED`（`app/schemas.py:27`），SPEC §6 状态机与 AC-19/AC-24 写的是 `SUBMITTED`。这是纯文档漂移，不影响行为，但本次修订 AC 时应一并勘误，避免 QA 按 SPEC 写出永远失败的用例。

## 7. 扩展性预留

### 7.1 上游 batch API 合并调用（明确本轮不做）

用户已确认「攒一批任务」的语义是**调度侧批量下发**：攒够 N 或等够 T 后一次性把这批任务放行给 worker，上游仍是**逐条 HTTP 调用**。本轮不做「合并成一次上游 batch API 调用」。

但为将来可能的演进，本 PRD 要求批量聚合的设计满足以下三条接口约束，使得未来接入上游 batch API 时**不需要改动客户端契约**：

1. **批次必须是一等概念**，有稳定的归组键与成员列表，而不仅仅是一个「放行定时器」的副产品。未来的合并调用需要能一次性拿到整批成员及其请求体。
2. **放行动作必须是一个可替换的策略点**。当前策略是「逐条 `publish_execute`」，未来可替换为「构造一次 batch 请求 + 分发结果到各成员」，替换点应收敛在一处，而不是散落在提交链路里。
3. **成员的独立身份必须保持**（R-18 / AC-59）。即便未来合并调用，每个成员仍需保有独立 task_id、独立状态、独立回放结果与独立回调——这是「加 `/async` 前缀即任务化」这个产品定位的底线，不能因为内部合并了调用就退化成「整批成功或整批失败」。

若未来做合并调用，届时需要新增的是**结果分发**能力（把一次 batch 响应拆回 N 个成员的 `upstream_response`）与**部分失败处理**语义，这两项是新的 PRD 主题，不在本轮预留范围内。

### 7.2 其他方向（仅登记，不承诺）

- 并发维度扩展到 model × user（现有 `data` 已有 `user_id`，数据层具备条件）；
- 基于上游实际拒绝率的自适应水位（当前所有上限均为人工静态配置）；
- 计划任务的周期性重复执行（cron 语义）——当前只支持一次性延迟/定时。
